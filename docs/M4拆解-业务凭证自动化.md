# M4-T02 业务→凭证自动化 拆解与实现方案

> 路线图 §6 M4-T02（L 级）。本文是 T02 单一设计真源。依赖 T01 总账基建（docs/M4拆解-总账基建.md）。
> 范围：凭证模板引擎——M3 单据**过账后自动生成对应记账凭证**，凭证可追溯源单据。
> **验收**：每张过账单据有且仅有一组对应凭证（含幂等：重复过账/重试不产生重复凭证）。

## 0. 范围界定
- **本批做**：四个采购/销售过账事件 → 自动凭证：采购入库 / 采购发票 / 销售出库 / 销售发票。
- **延后**（写明，避免范围膨胀）：期初建账 OPENING、盘点 COUNT_GAIN/LOSS、成本调整 COST_ADJUST 的凭证 → M4-T02 后续小批；**TRANSFER 调拨永不出凭证**（仓间移库账户层 1405 总额不变，无 GL 影响）。
- **勾稽影响**：在期初/盘点/调整凭证落地前，未来"存货 GL=库存子账"勾稽需排除 OPENING/COUNT/COST_ADJUST 流水（文档登记）。

## 1. 会计映射（已定稿）
### 1.1 暂估应付科目（方案A，V20 迁移）
采购"货到票未到"：入库时货已入但发票未到，formal 应付须等发票（与 accounts_payable 子账同时点），故入库贷方用**暂估应付**而非正式应付。拆 2202 为父 + 两个二级末级（与 V19 的 2221→222101/222102 同构；T01 尚无凭证引用 2202，迁移安全）：
- `2202 应付账款` → 改 `is_leaf=0`（非末级，不可直接挂账）
- `220201 应付账款—暂估应付款`（LIABILITY/CREDIT/leaf/preset，parent 2202，level 2）
- `220202 应付账款—应付账款`（LIABILITY/CREDIT/leaf/preset，parent 2202，level 2，**与 accounts_payable 子账勾稽**）

### 1.2 四事件分录表
| 源单据 post | 借 | 贷 | 金额来源 | voucherDate |
|---|---|---|---|---|
| 采购入库 PURCHASE_RECEIPT | 1405 库存商品 | 220201 暂估应付款 | `PurchaseReceipt.totalAmount()`（入库成本） | `receiptDate` |
| 采购发票 PURCHASE_INVOICE | 220201 暂估应付款 | 220202 应付账款 | `PurchaseInvoice.totalAmount()`（发票额） | `invoiceDate` |
| 销售出库 SALES_DELIVERY | 6401 主营业务成本 | 1405 库存商品 | `SalesDelivery.totalCogs()`（Σcogs） | **过账日 `LocalDate.now(UTC)`**（出库单无业务日；自动凭证在 post 同事务内生成，now=过账时点，与同刻 SALES_OUT 流水同期；**不依赖 createdAt**——restore 不恢复原值、语义脆弱；TODO 给 SalesDelivery 补 deliveryDate） |
| 销售发票 SALES_INVOICE | 1122 应收账款 | 6001 主营业务收入 | `SalesInvoice.totalAmount()`（发票额） | `invoiceDate` |

**金额差异**：暂估额（入库成本）与发票额可不等（部分开票/价差）；发票按**发票额**冲回暂估 → `220201` 余额 = 已收货未开票部分（正确业务表达，余额回零=全开票）。暂估价≠发票价的尾差留 220201，差异结转留后续，不影响凭证自平衡。
**COGS=0/金额≤0 边界**：`signum()<=0` 直接跳过生成（无金额无凭证；否则 `Voucher.create` 的"总额>0"会抛 `VoucherNotBalancedException`）。

## 2. 凭证模板引擎
- **`VoucherSourceType` 枚举**（domain `com.sjherp.domain.gl`，即 `source_doc_type` 列字典）：本批 4 值 PURCHASE_RECEIPT/PURCHASE_INVOICE/SALES_DELIVERY/SALES_INVOICE（带中文 label）。
- **`AutoVoucherService`**（app `com.sjherp.app.gl`，依赖 VoucherService + AccountingPeriodService + DocumentNumberGenerator）：四个明确方法 `generateForPurchaseReceipt(PurchaseReceipt, operator)` / `...PurchaseInvoice` / `...SalesDelivery` / `...SalesInvoice`（不引泛型策略表——4 类固定）；科目编码为类内常量（ACC_INVENTORY="1405" 等）。
- 每方法流程：①取金额，`signum<=0` return；②幂等查重 `findBySourceDocNo` 非空 return；③推算 period + 生成 VCH- 号；④确保账期 OPEN（§4）；⑤组装 `List<VoucherLineInput>`（借/贷两行，BigDecimal）；⑥`voucherService.createFromSource(...)` → DRAFT；⑦`voucherService.post(...)` → APPROVED；全程在业务 post 外层事务内。

## 3. 幂等与可追溯（验收核心）
- 幂等键 = `source_doc_no`（业务单号 PR-/PINV-/SD-/SINV- 全局唯一）。生成前 `findBySourceDocNo` 非空 → 跳过（每单据一组、重试不重复）。
- 主防线：业务单据状态机（COMPLETED 不可重过账，再过账抛 IllegalStateTransition）。纵深：**V20 `UNIQUE KEY uk_voucher_source (tenant_id, source_doc_type, source_doc_no)`** 替换 V19 非唯一 `idx_voucher_source`——自动凭证物理不可重复；T01 手工凭证 source 两列 NULL，MySQL 允许多行 NULL，不冲突。
- 领域改造：`VoucherService` 新增 `createFromSource(docNo, period, voucherDate, summary, VoucherSourceType sourceType, String sourceDocNo, lines, operator)`（回填 source 两列）；既有 `create` 重构为 `createFromSource(...,null,null,...)` 复用，**不破坏 T01 既有 create 签名/调用方**。

## 4. 集成机制（同事务直调）
四个 `*AppService.post` 内、业务过账之后、同 `@Transactional` 内直调 `autoVoucherService.generateForXxx(返回聚合, operator)`：
```java
@Transactional public PurchaseReceipt post(String docNo, String operator) {
    PurchaseReceipt receipt = purchaseReceiptService.post(docNo, operator);
    autoVoucherService.generateForPurchaseReceipt(receipt, operator);   // T02
    return receipt;
}
```
四处对称（销售出库 post 返回的 SalesDelivery 此时 totalCogs 已回填）。**否决事件方案**：DocumentStatusChangedEvent 不带单据类型 + SyncDomainEventPublisher 对监听器异常只 WARN 不外抛（吞异常破坏原子性）+ 财务凭证不可最终一致。装配：AutoVoucherService 加 GlInfraConfig @Bean；4 个 AppService 构造器新增 AutoVoucherService 参数（@Service 自动注入）。**无新增权限点**（自动凭证由业务过账权限驱动，非独立用户动作）。

## 5. 账期处理
- voucherDate 由各单据业务日推算 period（YearMonth→yyyyMM）；**出库单用 `LocalDate.now(UTC)` 过账日**（无业务日，与 SALES_OUT 流水同期，不依赖脆弱的 createdAt）。
- 账期不存在 → 自动 `open(period, operator)`（首次经营友好）；存在且 OPEN → 继续；**存在且 CLOSED → `VoucherService.post` 抛 `PeriodClosedException` → 回滚整个业务过账**（关账不可绕过，不自动 reopen）。判定用 try `get(period)` / catch NotFound → open。
- 并发边界：两笔同时向同一新账期过账，落后者 open 撞 `uk_period`（Spring DataIntegrityViolationException）→ 约束冲突污染事务、**整笔业务过账回滚可重试**；不在事务内强行 catch 续跑（彼时事务已 rollback-only）。小企业并发极低，已接受的已知风险。

## 8. 风险与决策
1 暂估模型方案A（220201 余额=已收未开票，部分开票留余额正确）；2 金额差异按发票额冲回、尾差留 220201；3 幂等=状态机+findBySourceDocNo+uk_voucher_source；4 关账期 CLOSED→回滚不 reopen、缺期自动 open；5 出库无业务日用 createdAt(UTC)；6 自动 open 并发撞键容错（已知风险）；7 COGS=0 跳过；8 范围只 4 事件（期初/盘点/调整延后，勾稽排除其流水）；9 T07 冲销靠 source_doc_no 定位原凭证红冲（本批 source 关联即锚点）；10 选直调否决事件（原子性）。
