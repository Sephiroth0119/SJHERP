# 业务文档：数据一致性校验 / 检查 Agent（M3-T13、M6-T05～T07）

> 面向业务与知识库。本文说明系统如何**自动核对账实**——库存流水、余额、成本、应收应付之间的勾稽关系，发现差错立刻上报（绝不静默修复）。这是 M3 里程碑的出口条件，也是 CLAUDE.md 原则 4 的落地。

## 1. 定位

ERP 最怕"账不平了还不知道"。SJHERP 内置一个**只读**的一致性校验器，把领域模型必须恒成立的勾稽关系固化为可随时运行的检查，产出结构化差异报告（break）。它**只查不改**：发现不一致只上报，由人判断处理——绝不自动"修正"，因为静默修复会掩盖真正的业务错误。

M6-T05 将检查统一成三个**显式运行来源**，每次都会生成 `CHK-` 运行编号并保存报告摘要：

- **`SCHEDULED` 定时巡检**：`@Scheduled` 检查 Agent；默认关闭（`sjherp.consistency.enabled=false`），生产可按 cron 开启，默认每日凌晨 3 点。
- **`MANUAL_API` 管理端运行**：`POST /api/consistency/runs`，仅 `ADMIN/BOSS` 可触发。
- **`AGENT` 聊天运行**：Agent 工具 `run_consistency_check`（NORMAL、只读、登录即可）；用户问“账对不对/有没有对不平/帮我核一下账”时调用。

兼容入口 `GET /api/consistency/check` 仍只供 `ADMIN/BOSS` 即时预览：它直接执行纯校验，不落运行报告、不发通知，也不会让关账动作产生重复报告。月末关账前置闸门同样继续直接调用纯 `ConsistencyCheckService.check()`。

## 2. 规则执行框架

- 规则经注册表稳定排序，**SQL 断言型规则始终先于 LLM 分析型规则**。现有生产链规则与 M6-T06 核心规则整体注册为 `CORE_SQL_ASSERTIONS`，原规则公式不拆写、不改口径。采购/销售三单勾稽各有独立稳定编码；当前 `ConsistencyCheckType` 共 21 个稳定编码。
- T05 默认没有生产 LLM 规则，也不发起模型调用，分析状态为 `SKIPPED`。未来 LLM 分析失败时采用 **fail-open**：已得到的确定性差异和完成报告继续保留，只把分析状态记为 `FAILED`，不把干净的 SQL 检查伪造成业务异常。
- LLM 规则只能接收结构化、最小化的确定性事实，不获得数据库连接或任意 SQL 能力；报告不保存提示词、模型原始响应或原始异常消息。

## 3. 校验的勾稽关系

| 组 | `ConsistencyCheckType` | 恒等式/规则 | 严重度 |
|---:|---|---|---|
| 1 | `LEDGER_QUANTITY` | 每个（仓库，商品）Σ库存流水数量 = 库存余额数量 | ERROR |
| 2 | `LEDGER_COST` | 每个（仓库，商品）Σ库存流水金额 = 库存余额结存金额 | ERROR |
| 3 | `NEGATIVE_BALANCE` | 库存余额数量、金额均不得为负 | 默认 ERROR；允许负库存时 WARN |
| 4 | `PAYABLE_AMOUNT` | 每张已过账采购发票生成的应付金额 = 发票金额 | ERROR |
| 5 | `RECEIVABLE_AMOUNT` | 每张已过账销售发票生成的应收金额 = 发票金额 | ERROR |
| 6 | `COGS_MISMATCH` | 销售出库行 COGS = 对应 `SALES_OUT` 流水金额绝对值合计 | ERROR |
| 7a | `PURCHASE_THREE_WAY` | 已开票采购量 ≤ 已收量 ≤ 采购订单量 | WARN |
| 7b | `SALES_THREE_WAY` | 已开票销售量 ≤ 已发量 ≤ 销售订单量 | WARN |
| 8 | `SETTLEMENT_ROLLUP` | 应收/应付 `settled_amount` = 对应核销记录金额合计 | ERROR |
| 9 | `SETTLEMENT_OVER` | 应收/应付 `settled_amount` ≤ 原金额，不得超额核销 | ERROR |
| 10 | `SETTLEMENT_STATUS` | `OPEN`/`PARTIAL`/`SETTLED` 与已核销金额、剩余余额严格互洽 | ERROR |
| 11 | `WORK_ORDER_COST_UNSETTLED` | 有完工产出的执行中/已完工工单应存在已过账成本结转行 | WARN（不阻塞关账） |
| 12 | `MATERIAL_ISSUE_COST` | 已完成领料/退料单回填成本 = 对应 `PRODUCTION_ISSUE`/`PRODUCTION_RETURN` 流水金额 | ERROR |
| 13 | `PRODUCTION_INBOUND_COST` | 已完成报工单入库成本 = 对应 `PRODUCTION_IN` 流水金额合计 | ERROR |
| 14 | `WORK_ORDER_MATERIAL_CONSERVATION` | 完工入库料费与领料净出库料费守恒；入库虚增超过 0.01 元为 ERROR，少于净领料表示在产料费 | ERROR / WARN；正向差额不超过 0.01 元不报 |
| 15 | `WORK_ORDER_COMPLETED_QTY` | 工单累计完工量 = 该工单已过账报工完工量合计 | ERROR |
| 16 | `COST_SETTLEMENT_ADJUST` | 成本结转行完工工费增量 = 对应 `COST_ADJUST` 库存流水金额合计 | ERROR |
| 17 | `PRODUCTION_INVENTORY_GL` | 生产存货成本 = 生产成本结算凭证 1405 科目净借方，差额不得超过 0.01 元 | ERROR |
| 18 | `GL_DETAIL` | 控制科目 1122 = OPEN/PARTIAL 应收未核销余额；220202（2202 正式应付末级）= OPEN/PARTIAL 应付未核销余额，按借减贷与红字冲销方向比较；这是控制科目总额勾稽，单据级来源由规则4/5及核销 rollup 提供 | ERROR |
| 19 | `VOUCHER_BALANCE` | 每张 APPROVED/REVERSED 凭证至少两行；每行金额非负且恰一侧为正；借贷合计相等且等于表头 total_amount | ERROR |
| 20 | `AUDIT_INTEGRITY` | 普通 APPROVED 匹配 voucher.post；红字 APPROVED 只匹配 voucher.reverse（DRAFT→APPROVED 的 document.status_changed 不能替代）；原 REVERSED 匹配 APPROVED→REVERSED 状态审计 | ERROR |

> 所有金额/数量比较用 `BigDecimal.compareTo`（按值比较，标度差不误报），报告值用 `toPlainString` 承载。

## 4. 报告、明细与通知

每次 `SCHEDULED`、`MANUAL_API`、`AGENT` 显式运行都保存一条摘要，记录来源、操作人、时间、完成/失败状态、是否干净、严重度计数和分析状态；**只有存在差异时才保存 break 明细**。干净运行因此有可追溯摘要，但没有空明细行。

每条 break 含：
- **类型**（如 LEDGER_QUANTITY / LEDGER_COST / PAYABLE / RECEIVABLE / COGS …）
- **键**（哪个仓库×商品 / 哪张单据）
- **期望值 vs 实际值**
- **严重度**：ERROR（账不平，必须查）/ WARN（数量越界等，需关注）。

`clean=true` 的唯一含义是**所有严重度的 finding 都为零**，即 ERROR、WARN、INFO 均为 0。`0 ERROR` 只表示没有阻塞关账的硬错误；若仍有 WARN（例如正常在产料费或未结转提醒），运行是非阻塞但并不干净，仍会保存差异并通知。有关账实差异时，按键定位到具体单据/库存项，人工排查根因（绝不让系统自动“抹平”）。报告列表与详情仅 `ADMIN/BOSS` 可查询；完整历史不通过普通聊天权限放宽。

通知遵循“干净静默、异常直达”的原则：

- 干净且成功的运行只保存摘要，**不发通知**。
- 任意差异或确定性运行失败，仅向当前**启用中且角色包含 `ADMIN` 或 `BOSS`** 的用户各投递一条站内通知；通知只含运行编号、来源和计数等安全摘要，不复制完整差异。
- 通知入口对所有已登录用户可见，但每人只能分页查看、统计未读和标记**自己的通知**；接收人由服务端当前用户强制派生，客户端不能指定或越权读取他人通知。
- 完成运行中出现 `ERROR` 即视为 P0：报告提交后向启用中的 ADMIN/BOSS 的 ACTIVE 会话追加一条幂等主动提醒。提醒只含运行编号和计数，不把差异正文塞进会话；会话中可继续询问报告，由 Agent 只读召回并解释真实明细。

运行报告、差异明细和站内通知均长期保留：只允许通知写入 `read_at` 标记已读，**不提供 REST `DELETE`、仓储删除方法或物理删除 SQL**。

## 5. 端到端验收证据

集成测试 `PurchaseToSalesFlowIntegrationTest`（`@Tag("integration-db")`，Testcontainers 真库，CI `backend-integration-db` job 运行）驱动完整链路：**期初进货 → 采购订单→收货→采购发票 → 销售订单→出库→销售发票**，全部过账后运行一致性校验，断言本链路 **0 个 ERROR break**，并用 SQL 旁证库存数量/金额、应付、应收、COGS 数值正确。另含负向用例：故意篡改余额后校验能命中库存数量 break——证明检查器不是空转。这是 M3-T11 / M3-T13 的共同验收。

## 6. 本阶段边界与相关资料

M6-T05 只建立规则注册、三来源运行、报告追溯和站内通知框架；M6-T06 在此基础上补齐 `GL_DETAIL`、`VOUCHER_BALANCE`、`AUDIT_INTEGRITY` 三类核心断言，并复用既有库存、核销、工单成本勾稽。`AUDIT_INTEGRITY` 的边界是运行时关键凭证状态/action 矩阵；全部领域写入口由 `AuditWriteCoverageTest` 静态防漂移，不在运行时 SQL 中宣称逐行覆盖所有业务表。M6-T07 只增加报告历史召回工具 `query_consistency_report` 与 P0 会话主动提醒：支持运行编号、UTC 自然日、`daysAgo=1`（昨天）和最近一次查询，返回安全摘要、解释和最多 10 条真实差异；所有已登录用户可召回，报告管理 API 仍仅 ADMIN/BOSS。主动提醒不新建会话、不自动修复、不引入新前端，企微/钉钉仍仅保留扩展契约，不做配置、鉴权或网络调用。
