# 业务文档：数据一致性校验 / 检查 Agent（M3-T13）

> 面向业务与知识库。本文说明系统如何**自动核对账实**——库存流水、余额、成本、应收应付之间的勾稽关系，发现差错立刻上报（绝不静默修复）。这是 M3 里程碑的出口条件，也是 CLAUDE.md 原则 4 的落地。

## 1. 定位

ERP 最怕"账不平了还不知道"。SJHERP 内置一个**只读**的一致性校验器，把领域模型必须恒成立的勾稽关系固化为可随时运行的检查，产出结构化差异报告（break）。它**只查不改**：发现不一致只上报，由人判断处理——绝不自动"修正"，因为静默修复会掩盖真正的业务错误。

三种触发方式：
- **随时查**：REST `GET /api/consistency/check`（ADMIN/BOSS）。
- **聊天问**：Agent 工具 `run_consistency_check`（NORMAL，只读）——用户问"账对不对/有没有对不平/帮我核一下账"时调用。
- **定时巡检**：`@Scheduled` 检查 Agent（默认关 `sjherp.consistency.enabled=false`，生产按 cron 打开，默认每日凌晨 3 点），发现 break 按严重度记日志告警（LLM 化上报留 M6-T06）。

## 2. 校验的勾稽关系

| 校验 | 恒等式/规则 | 严重度 | 业务含义 |
|---|---|---|---|
| 库存数量勾稽 | 每个(仓库,商品) Σ流水.quantity = 余额.quantity | ERROR | 流水与余额必须同源一致（库存账不破碎）|
| 库存成本勾稽 | 每个(仓库,商品) Σ流水.total_cost = 余额.cost_amount | ERROR | 移动加权成本恒等式 |
| 余额非负 | 余额.quantity ≥ 0（除非允许负库存）| ERROR/WARN | 默认禁止负库存 |
| 应付勾稽 | 应付账款 = 对应已过账采购发票金额 | ERROR | 每笔应付有发票来源 |
| 应收勾稽 | 应收账款 = 对应已过账销售发票金额 | ERROR | 每笔应收有发票来源 |
| COGS 勾稽 | 出库行 cogs_amount = 该出库 SALES_OUT 流水 Σ\|total_cost\| | ERROR | 销售成本与库存出账一致 |
| 采购三单数量 | 已开票量 ≤ 已收量 ≤ 订单量 | WARN | 采购数量单调勾稽 |
| 销售三单数量 | 已开票量 ≤ 已发量 ≤ 订单量 | WARN | 销售数量单调勾稽 |

> 所有金额/数量比较用 `BigDecimal.compareTo`（按值比较，标度差不误报），报告值用 `toPlainString` 承载。

## 3. 报告怎么读

返回结构：报告头（运行时间、break 总数）+ break 明细列表。每条 break 含：
- **类型**（如 LEDGER_QUANTITY / LEDGER_COST / PAYABLE / RECEIVABLE / COGS …）
- **键**（哪个仓库×商品 / 哪张单据）
- **期望值 vs 实际值**
- **严重度**：ERROR（账不平，必须查）/ WARN（数量越界等，需关注）。

**0 个 ERROR break = 账实一致**。有 break 时，按键定位到具体单据/库存项，人工排查根因（绝不让系统自动"抹平"）。

## 4. 端到端验收证据

集成测试 `PurchaseToSalesFlowIntegrationTest`（`@Tag("integration-db")`，Testcontainers 真库，CI `backend-integration-db` job 运行）驱动完整链路：**期初进货 → 采购订单→收货→采购发票 → 销售订单→出库→销售发票**，全部过账后运行一致性校验，断言本链路 **0 个 ERROR break**，并用 SQL 旁证库存数量/金额、应付、应收、COGS 数值正确。另含负向用例：故意篡改余额后校验能命中库存数量 break——证明检查器不是空转。这是 M3-T11 / M3-T13 的共同验收。
