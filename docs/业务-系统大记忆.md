# 系统大记忆业务说明

## 1. 解决什么问题

企业里的很多关键知识并不在单据字段里，而散落在老板、财务和业务人员的口头约定中，例如“什么算大客户”“采购准时率按哪个日期计算”“某类异常以后应当怎么处理”。如果这些知识只存在聊天记录或个人经验里，换人、换会话或系统升级后就容易丢失，也无法稳定复用。

系统大记忆把经过确认的业务知识保存为可追溯、可治理的正式记录。首批支持四类：

- `GAP_SOLUTION`：流程缺口已经确认的解决方案。
- `BUSINESS_TERM`：企业自己的业务术语和定义。
- `METRIC_DEFINITION`：指标名称、统计范围和计算口径。
- `OPERATION_PREFERENCE`：不破坏业务规则前提下的操作偏好。

大记忆不是业务单据，也不能替代领域规则。它不能绕过库存、财务、生产等领域服务修改业务数据。

## 2. 三个组成部分

| 组成 | 职责 | 是否可重建 |
|---|---|---|
| MySQL `memory_entry` | 保存完整原文、来源、版本、有效期、治理状态、索引状态和审计信息，是唯一真源 | 不适用，必须备份保护 |
| 本地 Ollama | 使用 `qwen3-embedding:0.6b` 把文本转换为 1024 维向量 | 可以从 MySQL 原文重新计算 |
| Qdrant | 保存向量及最小定位元数据，用于后续语义检索 | 可以从 MySQL 全量重建 |

Qdrant 不保存标题、原文、用户原话或业务正文。Ollama 只在本机运行，本批没有外部 Embedding 回退路径。

## 3. 写入与索引状态

创建记忆时，系统先在一个 MySQL 事务中保存真源。保存成功即代表记忆没有丢失；随后才生成向量并写入 Qdrant。

M6-T02 增加结构化写入通道。候选由记忆类型、标题、最多 50 项事实键值、来源和来源编号组成；金额、数量以十进制字符串承载。用户输入绑定当前 Agent 会话，缺口解决方案必须先通过 `GapRecordService` 解析真实 GapRecord。`write_memory` 是 HIGH 工具并要求 `memory:manage`，框架会持久化待确认调用，用户确认后才复用 `MemoryService` 写入。相同类型、来源、标题和事实生成稳定 `memoryKey`，确认重放不会重复新增。

- `PENDING`：真源已保存，正在等待首次索引或人工重建；此时不能声称已经可被语义召回。
- `INDEXED`：当前活动版本已按指定模型和维度写入 Qdrant。
- `FAILED`：真源仍然安全，但本地 Ollama、Qdrant或向量规格校验失败。系统会按退避时间自动重试，管理员也可以手工重试。

索引错误只保存脱敏摘要，不记录本地 URL、响应正文、记忆原文或密钥。达到自动重试上限后停止高频请求，等待管理员重试或全量重建。

## 4. 对话召回与引用

M6-T03 在每次已登录用户的聊天请求进入 LLM 前执行一次只读召回。系统使用当前问题生成查询向量，先从 Qdrant 取最多 12 个语义候选，再按候选主键批量回查 MySQL；只有当前租户、`ACTIVE + INDEXED`、已经生效且尚未过期的真源记录可以进入提示，最终最多保留 5 条。Qdrant 的旧点或错误状态不能绕过 MySQL 真源门禁。

召回结果以 `[M1]`、`[M2]` 等本次请求内引用编号注入系统提示，并携带类型、标题、来源类型、来源编号、生效时间和更新时间。回答采用记忆时应在 `text` 中标注对应引用并说明来源与时间；多条记忆冲突时应并列说明，不能静默替用户裁决。

记忆正文始终被视为不可信数据而不是指令。正文中的“忽略系统规则”“提升权限”等文字不会覆盖工具权限、HITL、领域状态机、实时工具结果或金额精度规则；正文经 JSON 转义后逐行注入，总上下文默认不超过 6000 字符。高风险确认恢复时沿用最近一条原始用户请求召回，不会拿“确认执行”作为查询。

召回对所有已登录聊天用户开放，不新增管理权限或独立召回 REST API；写入、替代、失效、重试和重建仍只允许持有 `memory:manage` 的 `ADMIN`/`BOSS`。Ollama、Qdrant 或格式化发生异常时召回会降级为空上下文，原聊天继续执行；降级日志只记录异常类型，不记录问题、正文、来源编号、URL 或响应体。

## 5. 版本与治理规则

记忆原文不可原地覆盖：

1. 更新活动记忆时，旧版本进入 `SUPERSEDED`。
2. 新记录沿用同一个 `memoryKey`，版本号加一，并保留 `previousId` 版本链。
3. 新版本以 `ACTIVE + PENDING` 进入索引流程。

失效操作把活动版本标记为 `EXPIRED`，不物理删除 MySQL 真源；对应 Qdrant point 属于可重建派生数据，可以删除。即使派生删除暂时失败，后续召回也必须回查 MySQL，只允许返回有效期内的 `ACTIVE` 版本。

M6-T04 提供确定性候选治理，但不替用户自动裁决业务语义：同租户、同类型、正文哈希相同的活动记忆进入“重复候选”；同租户、同类型、标题完全相同但正文哈希不同的活动记忆进入“冲突候选”。候选只从 MySQL 真源计算，不依赖 Qdrant，相似但未命中上述硬规则的内容仍由管理员人工判断。

冲突必须按完整候选组标记，组内活动版本统一进入 `CONFLICT`，对应 Qdrant point 删除；管理员可将仍在有效期内的冲突版本恢复为 `ACTIVE + PENDING` 并重新索引，也可将活动或冲突版本逻辑失效为 `EXPIRED`。`SUPERSEDED` 与 `EXPIRED` 是终态，不允许恢复。所有版本仍保留来源类型、来源编号、创建人、更新时间和统一审计日志，治理过程不物理删除 MySQL 真源。

## 6. 管理能力与权限

`/api/memories` 提供创建、单条查询、分页查询、版本替换、逻辑失效、手工重试索引和全量重建；M6-T04 追加 `/api/memories/governance/candidates` 候选查询、`/api/memories/governance/conflicts` 整组冲突标记和 `/api/memories/{memoryNo}/activate` 冲突恢复。管理页集中提供筛选查看、详情、编辑为新版本、失效、索引重试、重复候选处理、冲突标记与恢复，不提供物理删除按钮。

全部管理接口和页面均要求 `memory:manage`，仅 `ADMIN` 与 `BOSS` 持有；其他已登录角色仍只能通过聊天召回有效记忆。前后端均执行权限守门，后端权限是最终边界。

创建、替代、失效、冲突标记、冲突恢复、手工重试和全量重建都有审计记录。冲突批次审计只记录动作、数量和记忆编号；其他审计摘要只记录编号、记忆键、版本、类型和状态，均不复制标题、原文或正文哈希。

## 7. 本地运行

1. 启动 MySQL 与 Qdrant：`docker compose -f deploy/docker-compose.dev.yml up -d`。
2. 安装 Ollama，并执行 `ollama pull qwen3-embedding:0.6b`。
3. 设置 `SJHERP_MEMORY_ENABLED=true`。默认地址为 Ollama `http://localhost:11434`、Qdrant `http://localhost:6333`，可分别用 `SJHERP_OLLAMA_URL`、`SJHERP_QDRANT_URL` 覆盖。
4. 用 local profile 启动应用，通过 `/swagger-ui/index.html` 登录授权后调试管理接口。

召回默认参数为候选 12 条、最终 5 条、最低相似度 0.45、提示上限 6000 字符；可通过 `sjherp.memory.recall.*` 调整，越界配置会在启用大记忆时拒绝启动。

功能默认关闭。关闭时应用不会创建大记忆客户端，也不会连接 Ollama 或 Qdrant，原有 ERP 与 Agent 功能不受影响。

## 8. 当前边界

M6-T01 交付记忆真源、派生索引、版本治理、重试重建和管理入口；M6-T02 交付经 HITL 的结构化写入工具；M6-T03 交付聊天前置语义召回、MySQL 真源门禁、来源/时间引用和安全提示注入；M6-T04 交付确定性去重/冲突候选、人工状态治理和管理页面。语义相似度自动合并、自动裁决冲突、Agent 治理工具以及缺口解决后自动通知与回写均不在本阶段，后者仍属于 M6-T10。
