3. 编译/构建全绿（后端 `mvn install`，前端 `tsc + build`）
4. 涉及协议或领域模型变更：先改 docs，再改代码，三方（docs/Java/TS）一致
5. 不引入未登记的重量级依赖；架构级决策写 ADR

### 优先级标记

P0 = 阻塞下游 / v1.0 必须；P1 = v1.0 应有；P2 = v1.0 可裁剪。
规模估算：S（单 agent 一次任务）/ M（单 agent 多轮或 2–3 个并行任务）/ L（需拆成一组任务 + 交叉校验）。

## 13. Subagent 任务分配约定

1. 每个任务派发时引用本文编号，prompt 必含：读 CLAUDE.md + 相关 docs、验收标准、不许 git 操作（提交由主流程统一）。
2. 规模 L 的任务先派"拆解 agent"出子任务清单，再并行派发；完成后必派交叉校验 agent。
3. subagent 遇到的小决策（命名、内部结构）自行定夺并在返回中记录；触及协议、领域模型、依赖引入的决策必须上升。
4. 每个里程碑出口：交叉校验报告 + 本文档勾选更新 + CLAUDE.md「当前状态」同步。
5. 顺序铁律：库存写操作只能经 InventoryService（M3-T01 后任何绕过它的代码评审直接拒绝）；凭证不平不入库；已过账只冲销。
6. **模型分级派工（2026-06-13 起，控制 token 消耗）**：
   - **sonnet** —— 模式复制类：有现成样板可照抄的实现（CRUD 档案、按既有模式写 Controller/工具/测试、前端页面、文档同步、P2 清理）；
   - **opus** —— 复杂逻辑类：财务核算、凭证引擎、并发、安全、L 级任务拆解、**所有交叉校验 agent**；
   - **fable（主流程）** —— 编排、拆解审批、上升决策、合并验收、最终汇报。
   - 质量闸门不随模型降档：单测 + CI（含真库集成）+ opus 交叉校验三道闸对所有产出一视同仁；关键财务路径（成本/凭证/关账）实现用 opus。派工 prompt 的详尽程度不因模型降档而缩水。
7. **模块业务文档（2026-06-13 起）**：每个业务模块开发完成后，在 `docs/业务-<模块名>.md` 产出一份**业务文档**——面向业务而非代码：该模块解决什么业务问题、核心概念与单据/状态、关键业务规则与口径（尤其财务/成本/勾稽）、与其他模块的衔接、典型操作流程。目的是沉淀为「系统大记忆」知识库的素材（M6 大记忆会摄入这些文档），也方便非开发者理解系统能力。技术细节仍在拆解文档/ADR/代码注释中，业务文档不重复技术实现。已建模块（档案/库存/权限/审计/缺口）可按需回填。
