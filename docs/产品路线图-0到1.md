## 1. 发布定义与总体原则

### 版本阶段

| 版本 | 定义 | 退出标准（DoD） |
|---|---|---|
| v0.2 alpha | 内部可演示 | M1+M2 完成：登录后通过聊天完成基础档案维护，缺口通道可落库 |
| v0.5 beta | 1–3 家种子小企业真实试用 | M3+M4 完成：采购→入库→销售→出库→应收应付→月末结账全流程跑通，检查 Agent 日检无 P0 不一致 |
| v0.8 rc | 含生产模块的完整业务闭环 | M5+M6 完成：WO 工单与生产成本结转入账，大记忆问答可用，自进化闭环演示通过 |
| v1.0 | 可售卖 | M7+M8 完成：一键部署、备份恢复演练通过、安全基线、用户文档齐全、≥1 家付费意向客户完成一个完整会计期间 |

### 贯穿一切任务的验收底线（每个 subagent 任务的隐含 DoD）

1. 不违反 CLAUDE.md 五条不可妥协原则（数据模型不破碎 / 财务专业性 / 可审计 / 一致性可校验 / BigDecimal）
2. 领域层改动必须带单元测试；金额计算必须覆盖边界（四舍五入、负数、冲销）
3. 编译/构建全绿（后端 `mvn install`，前端 `tsc + build`）
4. 涉及协议或领域模型变更：先改 docs，再改代码，三方（docs/Java/TS）一致
5. 不引入未登记的重量级依赖；架构级决策写 ADR

### 优先级标记

P0 = 阻塞下游 / v1.0 必须；P1 = v1.0 应有；P2 = v1.0 可裁剪。
规模估算：S（单 agent 一次任务）/ M（单 agent 多轮或 2–3 个并行任务）/ L（需拆成一组任务 + 交叉校验）。

## 2. 里程碑总览与依赖

```
M1 Agent能力底座 ──┐
M2 档案+权限+审计 ──┼──► M3 进销存核心 ──► M4 财务核心 ──► M8 产品化收尾
        │           │         │
        │           │         └──► M5 生产模块 ──► (M4 生产成本入账部分)
        │           │
        └───────────┴──► M6 大记忆+检查Agent+自进化（骨架可提前，深化依赖 M3/M4 数据）
M7 前端体验：与 M3–M6 并行推进
X  横切（测试/CI/安全/协议演进）：自 M1 起持续
```

并行建议：M1 与 M2 可完全并行；M3 内部采购/销售两线可并行（共享库存与档案）；
M6-T01/T02（缺口通道、检查 Agent 骨架）可提前到 M1/M2 期间做。

## 13. Subagent 任务分配约定

1. 每个任务派发时引用本文编号，prompt 必含：读 CLAUDE.md + 相关 docs、验收标准、不许 git 操作（提交由主流程统一）。
2. 规模 L 的任务先派"拆解 agent"出子任务清单，再并行派发；完成后必派交叉校验 agent。
3. subagent 遇到的小决策（命名、内部结构）自行定夺并在返回中记录；触及协议、领域模型、依赖引入的决策必须上升。
4. 每个里程碑出口：交叉校验报告 + 本文档勾选更新 + CLAUDE.md「当前状态」同步。
5. 顺序铁律：库存写操作只能经 InventoryService（M3-T01 后任何绕过它的代码评审直接拒绝）；凭证不平不入库；已过账只冲销。
