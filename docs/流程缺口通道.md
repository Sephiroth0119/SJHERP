# 流程缺口通道（M1-T04）

> 状态：v1.0（2026-06 交付）
> 代码：`sjherp-domain` 的 `domain/gap` + `sjherp-infra` 的 `persistence/gap`（V5 迁移）+ `sjherp-app` 的 `app/gap`
> 关联：[CLAUDE.md](../CLAUDE.md)「流程缺口自进化闭环」第一环、[Agent执行循环.md](./Agent执行循环.md)、路线图 M6-T08/T10

## 1. 定位

用户向 Agent 提出系统当前做不到的需求时，Agent **不允许自由发挥绕过领域模型硬做**，
而是走专门的缺口记录通道：先与用户确认要点（普通选项卡片引导），再调用 `record_process_gap`
工具把缺口结构化落库。这是「用户提需求 → 记录缺口 → 开发 Issue → 自动补齐 → 写入大记忆」
自进化闭环的第一环。

## 2. 数据结构

聚合根 `GapRecord`（表 `gap_record`，V5 迁移，带 tenant_id，**不可物理删除**）：

| 字段 | 说明 |
|---|---|
| gapNo | 缺口编号 `GAP-年月-序号`（如 GAP-202606-0001），复用 `DocumentNumberGenerator` + `doc_sequence`，重启不重号 |
| sessionId | 来源会话 id（M6-T10 解决后回写通知原会话的依据；开发侧手工补录可空） |
| title / scenario / expectedBehavior / missingCapability | 缺口一句话 / 用户场景原文或复述 / 用户期望 / Agent 判断缺失的能力（全部必填） |
| businessModule | PURCHASE / SALES / INVENTORY / PRODUCTION / FINANCE / GENERAL |
| severity | LOW / MEDIUM / HIGH |
| status | 简单状态流转（**非**单据状态机，无冲销语义）：`NEW → TRIAGED → IN_DEVELOPMENT → RESOLVED`，每个非终态都可 `→ REJECTED`；RESOLVED / REJECTED 为终态。非法流转在领域层拒绝 |
| reporter | 提出人（userId 占位，M2-T05 登录后为真实用户） |
| 审计字段 | created_by/at、updated_by/at；缺口内容落库后不可修改，仓储更新只触碰 status 与审计尾巴 |

写操作唯一入口：`GapRecordService`（创建必填校验 + 自动编号；状态流转合法性检查；按状态/模块分页查询）。

## 3. Agent 工具与提示词约定

`record_process_gap`（app 层 `RecordProcessGapTool`，**常驻注册**非 dev-only，`GapInfraConfig`）：

- riskLevel = NORMAL：记录缺口不产生业务影响，不走框架高风险拦截；是否记录由提示词引导的**普通选项**（「帮我记录这个需求」/「不用了」）确认，不用 requiresConfirmation；
- 参数 schema：`title / scenario / expected_behavior / missing_capability / business_module(enum) / severity(enum)`，全部必填，框架执行前按 JSON Schema 校验；
- 执行即经 `GapRecordService` 落库，sessionId 取自 `ToolContext`，操作人记 `agent:<userId>`（审计区分 Agent 操作）；
- 返回缺口编号 + 引导文案，模型据此告知用户「已记录，开发团队会评估，解决后会通知你」。

系统提示词（`LlmAgent`）的「能力边界与流程缺口记录」段约定完整流程：
判断做不到 → 复述场景/期望并给选项 → 用户同意 → 调工具 → 回报 GAP 编号；
绝不在未调用工具时声称"已记录"或编造编号。

## 4. 查询 API（开发侧）

| 接口 | 说明 |
|---|---|
| `GET /api/gaps?status=&module=&page=&size=` | 分页列表（状态/模块筛选） |
| `GET /api/gaps/{id}` | 详情，不存在 404 `{"error"}` |
| `POST /api/gaps/{id}/status` body `{"status":"TRIAGED"}` | 状态流转（开发侧 triage/进入开发/解决/驳回），非法流转 400 `{"error"}` |

缺口创建只走 Agent 工具（聊天通道），API 不提供创建入口。

## 5. 与 M6 的衔接点

- **M6-T08（缺口 → Issue）**：以 `gap_record` 为数据源，对 `status=NEW` 的记录聚类去重后创建
  GitHub Issue（businessModule 作标签，scenario/expectedBehavior 作 Issue 正文），创建成功后流转
  `NEW → TRIAGED`；含人工审核开关。
- **M6-T09（开发者 Agent）**：领取 Issue 时流转 `TRIAGED → IN_DEVELOPMENT`，合并上线后 `→ RESOLVED`。
- **M6-T10（闭环回写）**：缺口 `RESOLVED` 时按 `sessionId` 通知原会话用户，并把解决方案写入大记忆。
