# SJHERP 备份与恢复（M8-T02）

目标：小企业把**财务真源（MySQL）**定时落到宿主机磁盘，出事时能灌回去并登录；Qdrant 只是大记忆派生索引，一并做快照，但救数以 MySQL 为准。

一键安装、升级、回滚边界仍看 [部署-一键安装.md](./部署-一键安装.md)。本篇只讲备份、定时、恢复和演练。

## 先记住这三条

1. **MySQL 必须备份。** 单据、凭证、库存、用户都在这里。丢了 volume 又没有 dump，财务数据救不回。
2. **Qdrant 可以重建。** 大记忆原文在 MySQL `memory_entry`；向量索引丢了，可在开启记忆后走管理端全量重建。快照是为了少做一次 Embedding，不是财务生命线。
3. **禁止把 `docker compose down -v` 当作常规恢复。** `-v` 会删掉 MySQL / Qdrant 的 named volume。恢复是「停应用 → 把备份灌进**仍在的**数据卷 → 再启动」，由 `./deploy/restore.sh` 做。

## 落盘路径与保留

| 内容 | 路径 | 说明 |
|---|---|---|
| MySQL dump | `deploy/backups/mysql/sjherp-<reason>-<UTC时间>.sql.gz` | `mysqldump --single-transaction --add-drop-database` |
| Qdrant 全库快照 | `deploy/backups/qdrant/sjherp-<reason>-<UTC时间>.snapshot` | `POST /snapshots`，再从 live 目录归档 |
| 最近一次 | `.../latest.sql.gz`、`.../latest.snapshot` | 符号链接，给演练/恢复用 |
| Qdrant live | `deploy/backups/qdrant/live/` | compose bind 到容器 `/qdrant/snapshots` |
| 升级前 dump | `reason=pre-upgrade` | `upgrade.sh` 调用 `backup.sh --mysql-only` |

以上文件在**宿主机磁盘**上，不在 Docker named volume 里。误执行 `down -v` 会清空库，但 `deploy/backups/` 通常还在——那是灾难收口，不是日常步骤。

保留天数：`deploy/.env` 的 `SJHERP_BACKUP_KEEP_DAYS`（默认 **14**，模板见 `deploy/.env.example`）。`backup.sh` 会删除超过该天数的 `sjherp-*.sql.gz` / `sjherp-*.snapshot`。请保证磁盘能放下大约「14 份库大小 + 快照」；监控告警留给 M8-T04。

密钥仍只在 `deploy/.env`，不要把 dump 提交进 git（`deploy/backups/.gitignore` 已忽略）。

## 立刻做：挂 cron

生产 compose **不在容器里跑 cron**（避免再引入一层调度镜像）。宿主机：

```bash
# 1. 先手动跑通一次
./deploy/backup.sh

# 2. crontab -e ，把路径换成仓库根（模板见 deploy/crontab.example）
15 2 * * * /bin/bash /ABS/PATH/TO/SJHERP/deploy/backup.sh >> /ABS/PATH/TO/SJHERP/deploy/backups/backup.log 2>&1
```

默认每天 **02:15 UTC**。脚本内部用 `flock`，重叠触发会失败而不是并行 dump。

compose 侧约定写在 `deploy/docker-compose.yml` 顶部注释和 `x-sjherp-backup`：备份脚本、目录、保留天数环境变量。不要把 MySQL/Qdrant 端口映射到公网来「方便备份」。

## 手工备份

```bash
./deploy/backup.sh                 # MySQL + Qdrant，并按保留天数清理
./deploy/backup.sh --mysql-only    # 只 dump 库
./deploy/backup.sh --qdrant-only   # 只打快照
./deploy/backup.sh --check         # 不写文件
```

升级脚本 `./deploy/upgrade.sh` 仍会在重建镜像前做一次 `--reason pre-upgrade` 的 MySQL dump（与 T01 相同时机，实现改为复用 `backup.sh`）。

## 恢复（覆盖当前数据，保留 volume）

先停业务入口，再灌备份。脚本会停 `nginx` / `app`，**MySQL 容器继续跑**，用 root 把 SQL 打进去；若带了 `--qdrant`，会在同一个 qdrant volume 里删除 storage **文件**（不是删 volume），再用官方 CLI `--storage-snapshot` 灌快照，最后按正常 compose 配置启动。

```bash
# 演练 / CI：跳过 YES 确认
./deploy/restore.sh --mysql latest --yes

# 生产：交互输入 YES
./deploy/restore.sh --mysql deploy/backups/mysql/sjherp-daily-XXXX.sql.gz

# 同时恢复 Qdrant 快照（可选；记忆关闭时通常不必）
./deploy/restore.sh --mysql latest --qdrant latest
```

之后建议：

```bash
./deploy/smoke.sh --login
```

若恢复的是**更旧代码对应的库**，应先检出旧版本再启动（Flyway 只向前），与 T01 回滚边界相同。

### 不要做的事

- `docker compose down -v` 再 `up`——这是删库，不是恢复。
- 在应用还连着库时手工 `DROP DATABASE`。
- 只恢复 Qdrant、不恢复 MySQL——救不回单据和凭证。
- 把 dump 拷进 git / 聊天记录。

误执行了 `down -v`、但宿主机上还有 `deploy/backups/mysql/*.sql.gz` 时：重新 `./deploy/install.sh` 起一套**空** volume，再 `./deploy/restore.sh --mysql <文件> --yes`。这是灾难收口，不要写成日常 runbook。

## 恢复演练（必须实测）

```bash
# 栈已经由 install.sh 拉起之后
./deploy/restore-smoke.sh
```

演练做了什么：

1. `backup.sh` 写出 MySQL gzip 与 Qdrant snapshot，并用 `gzip -t` 检查。
2. 在库里建 `sjherp_restore_drill_canary`（不在备份里）。
3. `restore.sh --mysql latest --qdrant latest --yes` 灌回。
4. 断言金丝雀表消失，`flyway_schema_history` / `sys_user` 行数与备份前一致。
5. `smoke.sh --login`：登录页、`/api/health`、admin 登录。

CI 的「部署资产」job 在一键安装冒烟之后跑同一条命令。本地没有完整栈时，至少：

```bash
./deploy/install.sh --check
./deploy/backup.sh --check
./deploy/restore.sh --check
./deploy/restore-smoke.sh --check
```
