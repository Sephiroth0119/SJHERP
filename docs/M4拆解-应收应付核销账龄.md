# M4-T03 应收应付核销/账龄 拆解与实现方案

> 路线图 §6 M4-T03（M 级）。本文是 T03 单一设计真源。依赖 M3 应收/应付台账（V15/V18）与 M4-T01/T02 总账。
> 范围：**核销引擎**（收款冲应收、付款冲应付，支持部分核销）+ **账龄分析**（只读）。
> **验收**：①部分核销累加、状态 OPEN→PARTIAL→SETTLED 正确推进、超额核销被拒；②账龄分桶 tie-out（Σ各桶=未核销余额、合计=全集未核销）；均真库验收。

## 0. 范围界定（T03 / T04 / T07 边界——本批最关键的设计裁定）

**核心会计洞见**：在复式记账下，*减少应收并收到现金* 是**同一笔经济业务**（借 银行存款/贷 应收账款）；不存在"应收已冲减但现金未收"的中间合法态。因此**脱离收付款的独立核销动作本身即记账错误**。据此裁定 T03/T04 边界：

- **T03 本批做**：
  1. **核销引擎**（domain）——把"对某笔应收/应付施加一次核销"的机制建好且单测充分：`AccountsReceivable.settle` / `AccountsPayable.settle`（推进 settled_amount + status，超额拒绝）、核销记录 `SettlementRecord`（**只追加**的审计/冲销锚点，原则 3 可审计）、`SettlementService`（装载→核销→保存子账→落核销记录）。
  2. **账龄分析**（app 只读）——基于现有应收/应付台账即可立刻产出，按客户/供应商分桶（未到期/逾期 1-30/31-60/61-90/90+ 天）。
  3. **核销历史查询**（app 只读）——按应收/应付 id 查其核销明细（验证记录表 + 用户可见核销轨迹）。
- **T03 不做（明确延后）**：
  - **收付款单（收款/付款登记）+ 现金/银行账户档案** → **T04**。
  - **核销的现金侧 GL 凭证**（借 银行/贷 1122 应收；借 220202 应付/贷 银行）→ **T04**（需银行账户主数据才能落"哪个现金/银行科目"）。
  - **本批 `SettlementService` 不生成 GL 凭证、不暴露独立 settle 的 REST/Agent 入口**：引擎仅供 T04 收付款单过账在**同事务内**触发（届时 T04 配套生成现金侧凭证）。
  - **核销冲销/红冲** → **T07**（按 `payment_doc_no` 定位核销记录反向）。
- **由此保证的不变量**：T03 上线后**无任何生产路径**会"只动子账不动 GL"——因为唯一会动子账的核销引擎在 T03 没有生产触发器（收付款单是 T04）。引擎的直接调用仅存在于单测/集成测试（测试内验证机制本身），不构成系统级账实分歧。M 级体量与此切分一致。
- **勾稽影响登记**：T13 一致性校验"应付子账 vs 220202 / 应收子账 vs 1122"在 T03 仍成立（生产无核销发生）；T04 落地收付款后，该勾稽需纳入已核销额与现金侧凭证，届时随 T04 更新。

## 1. 子账核销语义（已定稿）

### 1.1 settled_amount 是"可维护的汇总"，非可改的财务事实
`amount`（应收/应付原始金额）**永不变**（原则 2：财务记录只可冲销不可物理改/删）。`settled_amount` 是从**只追加**的 `settlement_record` 派生的运行汇总（同库存"流水只插入、余额维护"模式）。更新 `settled_amount` 不违反原则 2——真源是只追加的核销记录，`settled_amount` 是其维护型 rollup。`JdbcReceivableRepository.save` 已预留 UPDATE 路径（settled_amount/status），`JdbcAccountsPayableRepository.save` 本批补 UPDATE 路径。

### 1.2 AR/AP.settle（聚合内不变量）
新增 `settle(BigDecimal amount)`（AR 与 AP 对称）：
- 校验 `amount > 0`（≤0 抛 `IllegalArgumentException`）；金额 `setScale(AMOUNT_SCALE, ROUNDING)` 归一。
- `newSettled = settledAmount + amount`；若 `newSettled > this.amount` 抛 **`OverSettlementException`**（`extends IllegalArgumentException`，置于 `com.sjherp.domain.common` 避免 receivable↔settlement 包环）→ API 400。**绝不允许超额核销**。
- 落 `settledAmount = newSettled`；重算 `status`：`== amount → SETTLED`；`> 0 → PARTIAL`；（0 不会出现，因 amount>0）。
- 只动 `settledAmount`/`status`（二者本就非 final），其余字段 final 不动。
- 全额一次核销 → 直接 SETTLED；多次部分核销累加直到 SETTLED；已 SETTLED 再核销必触发超额拒绝（outstanding=0）。

## 2. 核销引擎（domain，新包 `com.sjherp.domain.settlement`）

- **`SettlementType`** 枚举：`RECEIVABLE("应收核销")` / `PAYABLE("应付核销")`（即 `settlement_type` 列字典）。
- **`SettlementRecord`** 聚合（`implements AuditTarget`，**只追加**）：字段 `id`(Long,落库回填)、`type`(SettlementType)、`targetId`(long，AR/AP 主键)、`targetSourceDocNo`(String，AR/AP 来源单号，追溯)、`amount`(BigDecimal>0,2 位)、`settlementDate`(LocalDate)、`paymentDocNo`(String,可空——T04 收付款单号回填)、`createdBy`、`createdAt`(Instant)。工厂 `record(...)`(校验 amount>0)/`restore(...)`/`assignId`。无任何改/删方法。
- **`SettlementRecordRepository`** 端口：`void save(SettlementRecord)`（回填 id）、`List<SettlementRecord> findByTarget(SettlementType, long targetId)`（核销历史，按 id 升序）、`List<SettlementRecord> findByPaymentDocNo(String)`（T04/T07 用，本批装好不调）。
- **`SettlementService`**（纯 Java，依赖 `ReceivableRepository` + `AccountsPayableRepository` + `SettlementRecordRepository`，app 层装配加事务边界）：
  - `@Audited` `settleReceivable(long receivableId, BigDecimal amount, LocalDate settlementDate, String paymentDocNo, String operator)`：`findById` 取 AR（无 → `ReceivableNotFoundException`）→ `ar.settle(amount)` → `receivableRepo.save(ar)`(UPDATE) → 建 `SettlementRecord(RECEIVABLE, ar.id, ar.sourceDocNo, amount, date, paymentDocNo, operator)` → `settlementRepo.save` → 返回记录。
  - `@Audited` `settlePayable(long payableId, ...)`：对称（`AccountsPayableRepository.findById` 本批新增 → 无 → `PayableNotFoundException`；`ap.settle` → `payableRepo.save`(UPDATE 路径本批补) → 落 PAYABLE 记录）。
  - 只读：`findReceivableSettlements(long arId)` / `findPayableSettlements(long apId)` → `findByTarget`。
  - 校验 operator 非空；settlementDate 非空。
- **异常**：`OverSettlementException`（common）、`PayableNotFoundException`（payable 包，照 `ReceivableNotFoundException`）。
- **端口缺口补齐**：`AccountsPayableRepository` 新增 `Optional<AccountsPayable> findById(long id)`（AR 端口已有；JDBC 实现补）。

## 3. 持久化（infra）

- **`JdbcSettlementRecordRepository`**（`com.sjherp.infra.persistence.settlement`，照 `JdbcReceivableRepository` 风格）：INSERT + 回填 id（settle 只产生新记录，记录本身永不更新）；`findByTarget`/`findByPaymentDocNo` 只读。tenant_id 恒 0。created_at 按 UTC 写。
- **`JdbcAccountsPayableRepository`** 改：①`save` 增 `id != null → UPDATE accounts_payable SET settled_amount=?, status=? WHERE id=?`（照 AR 实现，移除"非空即 return"早退）；②新增 `findById` 覆写（`WHERE tenant_id=0 AND id=?`）。
- **V21 迁移** `V21__settlement_record.sql`（DDL 风格照 V18）：
  ```sql
  CREATE TABLE settlement_record (
    id                   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id            BIGINT UNSIGNED NOT NULL DEFAULT 0,
    settlement_type      VARCHAR(16)  NOT NULL COMMENT 'RECEIVABLE/PAYABLE',
    target_id            BIGINT UNSIGNED NOT NULL COMMENT 'accounts_receivable.id 或 accounts_payable.id',
    target_source_doc_no VARCHAR(64)  NOT NULL COMMENT 'AR/AP 来源单号（追溯）',
    amount               DECIMAL(18,2) NOT NULL COMMENT '本次核销金额(>0)',
    settlement_date      DATE         NOT NULL COMMENT '核销业务日',
    payment_doc_no       VARCHAR(64)  NULL COMMENT '收付款单号（M4-T04 回填；T03 恒 NULL）',
    created_by           VARCHAR(64)  NOT NULL,
    created_at           DATETIME(6)  NOT NULL,
    PRIMARY KEY (id),
    KEY idx_settlement_target  (tenant_id, settlement_type, target_id, id),
    KEY idx_settlement_payment (tenant_id, payment_doc_no)
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='核销记录（应收应付核销流水，M4-T03，只追加）';
  ```
  不设 `payment_doc_no` 唯一约束（一张收付款单可核销多笔应收/应付；唯一形态留 T04 收付款单驱动时定）。

## 4. 账龄分析（app 只读，`com.sjherp.app.finance`）

- **`AgingReportDao`**（`@Repository` 自动扫描，照 `ReportQueryDao`：零写库、金额 DECIMAL 精确聚合、**主表 LEFT JOIN customer/supplier 绝不静默丢行**）：
  - `receivableAging(asOf, customerId?, page, size)` / `payableAging(asOf, supplierId?, page, size)`。
  - 仅取**未结清**（`status <> 'SETTLED'` 等价 `amount - settled_amount > 0`）；分桶基于**未核销余额** `amount - settled_amount`。
  - 逾期天数 = `asOf - dueDate`（AR `dueDate` 可空 → `COALESCE(due_date, DATE(created_at))`；AP `due_date` 非空）。桶：`未到期`(逾期≤0)、`逾期1-30`、`逾期31-60`、`逾期61-90`、`逾期90+`。SQL 用 `CASE` 按桶 `SUM`。
  - 输出**按客户/供应商汇总**（每行：counterparty + 5 桶金额 + 该 counterparty 未核销合计）+ 全过滤集**总计行**（grandTotal 各桶 + 总未核销）。明细级核销/单据已由现有 `/api/receivables`、`/api/payables` 提供，不重复。
  - `asOf` 由 controller `LocalDate.now()` 默认（app 层取当前日合法）。分页 `MAX_SIZE=200`。
- **DTO** `AgingDtos`：金额一律 `toPlainString()`（精度原则）；桶字段命名 `notDue/overdue1To30/overdue31To60/overdue61To90/overdue90Plus/totalOutstanding`。
- **`AgingReportController`**（`@RequestMapping("/api/reports")`，与 T12 报表同前缀；与 ReportController 不冲突——全路径唯一）：
  - `GET /api/reports/receivable-aging?asOf=&customerId=&page=&size=`
  - `GET /api/reports/payable-aging?asOf=&supplierId=&page=&size=`
  - 均 `@PreAuthorize("@perm.has('finance:settlement')")`（账龄暴露对手方余额+逾期，敏感）。`asOf` 缺省今天。`@ExceptionHandler(IllegalArgumentException)` → 400。

## 5. 核销历史查询（app 只读）

- **`SettlementReadAppService`**（`@Transactional(readOnly=true)`）：`findReceivableSettlements(arId)` / `findPayableSettlements(apId)` → SettlementService 读。
- **`SettlementController`** `GET /api/settlements?type=RECEIVABLE|PAYABLE&targetId=`（`@perm.has('finance:settlement')`）→ 该应收/应付的核销记录列表（金额字符串、含 paymentDocNo 可空）。`type` 非法 → 400。

## 6. 装配与权限

- **`SettlementInfraConfig`**（`com.sjherp.app.config`，照 `SalesInfraConfig`）：`@Bean SettlementRecordRepository`(new JdbcSettlementRecordRepository(jdbc))、`@Bean SettlementService`(注入 ReceivableRepository+AccountsPayableRepository+SettlementRecordRepository 既有/新 Bean)。`AgingReportDao` 走 `@Repository` 自动扫描；Controller/AppService 走组件扫描。
- **权限点**：`Permission` 新增 `FINANCE_SETTLEMENT("finance:settlement", "应收应付核销与账龄")`（紧随 FINANCE_VOUCHER）。`RolePermissions`：ADMIN/BOSS/ACCOUNTANT 授予（与 finance:voucher 同档；核销是会计日常）。本批仅**只读**端点用它；写动作（settle）的 REST/Agent 入口在 T04，届时复用本权限点。`RolePermissionsTest` 同步断言。

- **集成（@Tag integration-db 真库）**：
  - `SettlementEngineIntegrationTest`：造应收/应付（经发票过账或直插测试夹具）→ `SettlementService.settleReceivable/settlePayable` 部分+全额 → 断言子账 settled_amount/status 落库、核销记录行数/金额/追溯正确、超额核销被拒（DB 态不变）。

## 9. 风险与决策

1 **T03/T04/T07 切分**（§0）：核销引擎=T03（只动子账+只追加记录，不出 GL、不暴露独立写入口）；收付款单+银行账户+现金侧凭证=T04（触发引擎）；冲销=T07。脱离收付款的独立核销即记账错误，故引擎无生产触发器→无账实分歧。
2 settled_amount 为只追加核销记录的维护型 rollup，更新它不违反原则 2（真源是 settlement_record）。
3 超额核销硬拒绝（OverSettlementException），部分核销累加、状态机 OPEN→PARTIAL→SETTLED。
4 账龄基于未核销余额、未结清记录，桶=未到期/1-30/31-60/61-90/90+；AR 空 dueDate 用 COALESCE(due_date, created_at)；报表主表 LEFT JOIN 绝不静默丢行（财务产出红线）。
5 OverSettlementException 置 common 避免 receivable/payable↔settlement 包环。
6 payment_doc_no 本批恒 NULL、不设唯一约束（留 T04）；记录表为 T07 红冲锚点（按 payment_doc_no 反查）。
7 finance:settlement 权限点本批仅护只读端点，T04 写动作复用。
8 一致性勾稽（T13）在 T03 仍成立（无生产核销）；T04 落收付款后纳入已核销额+现金侧凭证，随 T04 更新（登记）。
