# ADR-001 热部署策略

- 状态：**提议**
- 日期：2026-06-11
- 关联：CLAUDE.md「流程缺口自进化闭环」、自研 Agent 框架设计要点「状态显式持久化」

## 背景

项目核心闭环要求：用户提出流程缺口 → 开发者 Agent 自动开发补齐 → **热部署上线**，期间不能丢失进行中的 Agent 会话，更不能破坏数据模型完整性（不可妥协原则 1）。需要选定新能力上线的技术路线。

## 候选路线对比

### 路线 A：插件化 ClassLoader（动态加载扩展 jar）

- 优点：真正的运行期热插拔，不中断服务；扩展与核心隔离清晰。
- 缺点：实现复杂度高——类卸载/内存泄漏、Spring 上下文与事务代理的集成、插件间依赖冲突；插件 API 边界需要先成熟稳定才值得做。
- 风险：项目早期领域服务接口频繁变动，插件边界会反复返工。

### 路线 B：嵌入脚本引擎（Groovy / JS 等运行期执行）

- 优点：上线最快，改脚本即生效。
- 缺点：脚本天然容易绕过领域服务层与状态机校验，与不可妥协原则 1 直接冲突；类型安全弱、难测试、难审计。
- 风险：等于给 Agent 一条"自由写库"的旁路，**原则上不可接受**。

### 路线 C：Agent 会话状态持久化 + 快速滚动重启

- 做法：会话状态全部落库（框架既定设计），新代码以普通模块合入后快速重启进程（单机秒级 / 后续双实例滚动），重启后会话从持久化状态无缝恢复，用户侧仅感知短暂等待。
- 优点：实现成本最低；新能力走正常代码路径（领域服务 + 状态机 + 测试 + 审计），完全不破坏原则；"状态持久化"本来就是框架必做项。
- 缺点：不是真·热部署，有秒级窗口；上线频率受重启成本约束。

## 结论（倾向）

**先做路线 C（状态持久化 + 快速滚动重启）**：

1. 它把成本花在无论如何都要做的"会话状态持久化"上，零额外架构风险。
2. 路线 A（插件化 ClassLoader）作为后续演进方向，待领域服务接口稳定后**另开 ADR** 评估补齐。
3. 路线 B 否决：与数据模型完整性原则冲突，不再考虑。

## 影响

- sjherp-agent 模块必须从第一天起保证：任意时刻杀进程，会话可从数据库完整恢复。
- 部署脚本需支持快速重启与健康检查；后续演进到双实例滚动发布。
