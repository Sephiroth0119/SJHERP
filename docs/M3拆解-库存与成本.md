## 0. 结论速览

| 决策点 | 结论 |
|---|---|
| 加权单价存储 | **不冗余存储**，实时由 `cost_amount / quantity` 计算（派生值） |
| 余额真源 | `quantity`（DECIMAL(18,6)）+ `cost_amount`（DECIMAL(18,2)）两列，对账只认这两列 |
| 流水可变性 | inventory_transaction **只插入、不更新不删除**，纠错走反向流水（冲销单驱动） |
| 流水走状态机？ | **不走**。流水是过账结果，不是单据；产生流水的单据（盘点/调拨/成本调整单）才走 BusinessDocument |
| 并发 | balance 行 `SELECT ... FOR UPDATE`，多行按 `(warehouse_id, product_id)` 升序加锁 |
| 负库存 | 默认禁止，配置开关 `sjherp.inventory.allow-negative-stock`，拒绝抛 `InsufficientStockException` |
| 舍入 | 单价 DECIMAL(18,6) HALF_UP，金额 DECIMAL(18,2) HALF_UP；**出空清零**吸收尾差 |
| 幂等 | 每笔流水带必填 `idempotency_key`（唯一键兜底），同键同参返回首次结果，同键不同参抛异常 |
| D-8 | **必须在 T01b 开工前还清**（InventoryService 是全仓第一个跨表外层事务） |

## 1. 领域模型设计

### 1.1 inventory_balance（V10 迁移）

仓库×商品一行（`UNIQUE(tenant_id, warehouse_id, product_id, batch_id)`）。列：id、tenant_id（恒 0）、warehouse_id、product_id、**batch_id BIGINT NOT NULL DEFAULT 0**（Q-2/批次预留：v1.0 恒 0 不建批次表，未来启用批次免重建唯一索引）、quantity DECIMAL(18,6)、cost_amount DECIMAL(18,2)、updated_by/updated_at。

**单价不冗余存储的理由**：单价是 `cost_amount/quantity` 的派生值，存两份必然漂移（见 §2 案例第 4 步：扣减后反算单价 10.894455 ≠ 出库时点 10.894444，这是正常现象而非误差）；对账、检查 Agent（M6-T06）只校验数量与金额两条等式，单价仅在读取/报表时按 6 位 HALF_UP 现算。数量一律**基本单位**记账（多单位换算在单据行层完成，本服务不做换算——防双重换算）。

### 1.2 inventory_transaction（V10 迁移）

只追加流水，列：id、tenant_id、warehouse_id、product_id、batch_id（恒 0）、txn_type、quantity（**带符号**：入库正/出库负/成本调整 0）、unit_cost DECIMAL(18,6)（入库=入库单价；出库=出库时点加权单价快照；成本调整 NULL）、total_cost DECIMAL(18,2)（与 quantity 同号；成本调整=调整额可正可负）、**balance_quantity_after / balance_amount_after**（过账后余额快照，对账与排错利器）、src_doc_type、src_doc_no、src_line_no、idempotency_key（`UNIQUE(tenant_id, idempotency_key)`）、operator、created_at。索引 `(tenant_id, warehouse_id, product_id, id)`。

带符号设计使对账 SQL 一行写完：`SUM(quantity)=balance.quantity AND SUM(total_cost)=balance.cost_amount`。

`InventoryTxnType` 枚举：`OPENING` 期初 / `PURCHASE_IN` 采购入库 / `SALES_OUT` 销售出库 / `COUNT_GAIN` 盘盈 / `COUNT_LOSS` 盘亏 / `TRANSFER_IN` 调拨入 / `TRANSFER_OUT` 调拨出 / `COST_ADJUST` 成本调整。每个类型固定方向（IN/OUT/NEUTRAL），与 quantity 符号由服务强制一致。

### 1.3 InventoryService —— 唯一写入口（CLAUDE.md 原则 1，路线图 §13 铁律）

```java
public class InventoryService {                       // domain/inventory，纯 Java，app 层装配并加事务
    StockMovementResult inbound(InboundCommand cmd);          // 入库：unitCost 必填（>=0），算 totalCost
    StockMovementResult outbound(OutboundCommand cmd);        // 出库：成本由服务按移动加权计算并返回
    StockMovementResult adjustCost(CostAdjustCommand cmd);    // 成本调整：数量不变，只调金额
    List<StockMovementResult> execute(List<StockMovementCommand> batch); // 批量同事务原子（调拨=一出一入）
    InventoryBalanceView balanceOf(long warehouseId, long productId);    // 只读
}
```

- Command 公共字段：warehouseId、productId、quantity（正数 BigDecimal，基本单位）、txnType、srcDocType/srcDocNo/srcLineNo、**idempotencyKey（必填）**、operator。`InboundCommand` 加 unitCost；`CostAdjustCommand` 用 adjustAmount（可负）。
- `StockMovementResult` 返回流水 id、计算出的 unitCost/totalCost、过账后余额——**销售出库单由此取 COGS**，工单领料（M5-T04）同口径复用。
- 幂等约定：`idempotencyKey = docType:docNo:lineNo`（如 `SALES_DELIVERY:SD-202606-0001:1`）。撞唯一键时读回原流水，参数一致→返回原结果（真幂等，支持单据过账重试）；不一致→抛 `IdempotencyConflictException`（防键误用静默吞单）。
- 校验：仓库/商品存在且启用、quantity>0（adjustCost 除外）、txnType 方向与方法匹配；违反抛领域异常（IllegalArgumentException 族）。

### 1.4 并发策略

- 事务边界：app 装配时 InventoryService 方法级 `@Transactional`（**全仓第一个跨表外层事务——D-8 触发点**）。
- 每次过账：`SELECT ... FOR UPDATE` 锁 balance 行 → 计算 → UPDATE balance + INSERT transaction 同事务提交。行不存在时 INSERT 初始零行，撞唯一键退回锁行路径（同 `JdbcSequenceProvider` 模式）。
- **锁顺序约定（防死锁）**：一个事务锁多个 balance 行（批量/调拨）时，先对涉及行集按 `(warehouse_id, product_id)` 升序排序再依次 FOR UPDATE。调拨 A→B 与 B→A 并发是典型死锁场景，T01d 必测。
- 单据取号仍走 `JdbcSequenceProvider` REQUIRES_NEW（独立短事务），**取号必须在锁 balance 行之前完成**，避免行锁持有期间叠加 doc_sequence 锁。

### 1.5 负库存策略

- 默认禁止：出库后 `quantity < 0` 时抛 `InsufficientStockException`（含仓库/商品/现存量/需求量，Agent 可读文案），整个事务回滚。
- 配置开关 `sjherp.inventory.allow-negative-stock=true` 时仅解除数量校验，成本口径退化：出库前 `quantity > 0` 照常加权；`quantity <= 0` 时单价无法计算，取该仓该商品**最近一笔流水的 unit_cost**，连流水都没有则仍拒绝。负库存期间成本是估计值，回正后**不追溯重算**（v1.0 简化，写入文档与检查 Agent 规则：负库存行标红上报）。
- 负成本路径：负库存关闭（默认）时 `quantity >= 0` 恒成立，`cost_amount` 由出空清零规则保证 ≥ 0——**不存在负成本状态**，T01a 单测断言之。

### 1.6 移动加权成本算法 —— 精确口径（对账能否平的关键）

1. **入库**（OPENING/PURCHASE_IN/COUNT_GAIN/TRANSFER_IN）：`total = (unitCost × qty).setScale(2, HALF_UP)`；余额 `quantity += qty`、`cost_amount += total`。舍入只发生在 total 这一步。盘盈默认按当前加权单价入库（零库存盘盈必须指定成本）。
2. **出库**（SALES_OUT/COUNT_LOSS/TRANSFER_OUT）：
   a. `unitCost = cost_amount.divide(quantity, 6, HALF_UP)`（出库时点加权单价，写入流水快照）；
   b. `total = (unitCost × qty).setScale(2, HALF_UP)`；
   c. **出空清零**：若出库后 `quantity == 0`，则 `total = 出库前 cost_amount` 全额带走（覆盖 b 的结果），保证不残留"数量 0 金额非 0"的尾差行；
   d. 余额 `quantity -= qty`、`cost_amount -= total`。**用已舍入的 total 扣减**，使"余额金额 = Σ流水 total_cost"严格成立——这是对账恒等式，绝不能用未舍入中间值扣。
3. **零库存后首次入库**：余额行已是 (0, 0.00)，按 1 正常累加，单价自然 = 本次入库价（§2 第 10 步验证）。
4. **成本调整单（COST_ADJUST）语义**：数量不变、`cost_amount += adjustAmount`（典型场景：到票价差、运费入成本）。约束：当前 `quantity > 0`（无数量无成本可调），调整后 `cost_amount >= 0`，否则拒绝。调整即时改变后续出库加权单价。
5. 调拨成本：调出按出库口径计成本，调入用**调出流水的 total/qty 原值**入库（金额守恒，两腿同事务）。

### 1.7 与既有基建的关系

- **流水不走 BusinessDocument**：流水是不可变的过账结果，无生命周期；盘点单（`SC-年月-序号`）、调拨单（`TR-`）、成本调整单（`CA-`）是单据，走状态机，在 `COMPLETED`（或 EXECUTING→过账钩子）时调 InventoryService 产生流水；冲销时由红字单驱动产生反向流水。期初导入（M2-T09）doc_type=OPENING，doc_no 用导入批次号 `OP-年月-序号`。
- **审计**：InventoryService 写方法照例 `@Audited`（inventory.inbound/outbound/adjust_cost，AuditWriteCoverageTest 会强制）；单据状态流转经 `SyncDomainEventPublisher` 自动落审计。⚠️ **D-8 不还清不得装配**：外层事务 + REQUIRES_NEW 审计 = 回滚后留幽灵审计。修复（建议 b 方案：`TransactionSynchronization.afterCommit` 插审计，保留"审计失败不阻塞"）必须先行，见 §3。
- **tenant_id** 照例：新表全带、恒 0、入唯一键最左前缀；领域层不出现租户概念（ADR-002）。
- **Q-2 预留**：成本计算抽 `CostingStrategy` 接口（v1.0 唯一实现 MovingWeightedAverage），全局配置 `sjherp.inventory.costing-method=MOVING_AVERAGE`，FIFO 留实现位不留死代码。
- 权限点：新增 `INVENTORY_ADJUST("inventory:adjust")`（期初/调整写入口；查询照例不设权限点）。Warehouse/Product 停用前"非零库存"引用检查（M2 遗留 TODO）在 T01c 顺手补上。

## 2. 教科书对账案例（T01a 单测必须逐步断言以下全部数字）

商品 P（基本单位：个），仓库 WH1。口径：单价 6 位 HALF_UP、金额 2 位 HALF_UP、出空清零。
表中"加权单价"为派生展示值（`金额/数量`，6 位 HALF_UP），出库成本用的是**出库时点**算出的 unit_cost。

| # | 动作 | 流水 quantity | 流水 unit_cost | 流水 total_cost | 余额数量 | 余额金额 | 派生加权单价 |
|---|---|---|---|---|---|---|---|
| 1 | 期初 100 个 @10.00 | +100 | 10.000000 | +1000.00 | 100 | 1000.00 | 10.000000 |
| 2 | 采购入库 50 @12.50 | +50 | 12.500000 | +625.00 | 150 | 1625.00 | 10.833333 |
| 3 | 采购入库 30 @11.20 | +30 | 11.200000 | +336.00 | 180 | 1961.00 | 10.894444 |
| 4 | 销售出库 70 | −70 | 10.894444 | −762.61 | 110 | 1198.39 | 10.894455 |
| 5 | 采购入库 40 @9.80 | +40 | 9.800000 | +392.00 | 150 | 1590.39 | 10.602600 |
| 6 | 盘亏 5 | −5 | 10.602600 | −53.01 | 145 | 1537.38 | 10.602621 |
| 7 | 成本调整 +12.62（运费入成本） | 0 | （NULL） | +12.62 | 145 | 1550.00 | 10.689655 |
| 8 | 销售出库 100 | −100 | 10.689655 | −1068.97 | 45 | 481.03 | 10.689556 |
| 9 | 销售出库 45（**出空清零**） | −45 | 10.689556 | −481.03 | 0 | 0.00 | — |
| 10 | 零库存后采购入库 20 @8.00 | +20 | 8.000000 | +160.00 | 20 | 160.00 | 8.000000 |

关键步骤验算（实现 agent 复核用）：
- 步 4：unit_cost = 1961.00/180 = 10.894444（10.89444̄4 截 6 位）；total = 10.894444×70 = 762.61108 → 762.61；余额 1961.00−762.61 = 1198.39。扣减后派生单价 1198.39/110 = 10.8944545… → 10.894455 ≠ 10.894444：**正常漂移，非 bug**（单价不存储的论据）。
- 步 6：unit_cost = 1590.39/150 = 10.602600（整除验证点）；total = 53.013 → 53.01（HALF_UP 第三位 3 舍）。
- 步 8：unit_cost = 1550.00/145 = 10.6896551… → 10.689655；total = 1068.9655 → **1068.97**（HALF_UP 进位验证点）。
- 步 9：按公式 481.03/45 = 10.6895555… → 10.689556，×45 = 481.03002 → 481.03，与清零规则**恰好一致**；但断言必须验证规则路径（total 直接取出库前 cost_amount），并补一个公式结果≠余额的出空构造用例（如余额 10.00/3 个出 3 个：公式 3.333333×3=10.00 ✓，再构造 100.00/30 出 30：3.333333×30=99.99999→100.00 ✓；用 0.10/3 出 3：0.033333×3=0.099999→0.10 ✓——构造性差异困难恰说明清零规则是兜底保险，单测可直接桩验证分支）。
- 全程对账恒等式：Σ流水 quantity = 100+50+30−70+40−5+0−100−45+20 = **20** = 期末数量；Σ流水 total_cost = 1000+625+336−762.61+392−53.01+12.62−1068.97−481.03+160 = **160.00** = 期末金额。✓
- 补充断言：步 4 之后任一时点尝试出库超过现存量 → `InsufficientStockException` 且余额与流水均无变化；步 9 之后 quantity=0 时 adjustCost → 拒绝；全程 cost_amount ≥ 0。
