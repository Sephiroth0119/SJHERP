# SJHERP 性能基线（M8-T05）

面向**小企业私有部署**：几十人同时过账、库存流水长到百万行时，过账路径不该退化成全表扫描。不是 k6 云压测，也不引入 Grafana / Prometheus Server。

一键安装见 [部署-一键安装.md](./部署-一键安装.md)；备份见 [部署-备份恢复.md](./部署-备份恢复.md)；HTTPS 见 [部署-安全基线.md](./部署-安全基线.md)；监控见 [部署-监控告警.md](./部署-监控告警.md)。

## 1. 目标与口径

| 项 | 口径 |
|---|---|
| 并发用户 | 小企业目标 **50**。压测里每位用户过自己的仓库×商品（避免人为把所有人锁在同一 SKU 上；同 SKU 行锁串行化是正确性，M3 已有 20 线程专项） |
| 单表百万行 | `inventory_transaction` 合成到 ≥ 1 048 576 行后，过账热查询仍走索引 |
| 过账路径 | 库存唯一写入口 `InventoryService` + 采购入库单 `PurchaseReceiptService.post`（单据过账） |
| 正确性 | 并发结束后对账恒等式 Σ流水 = 余额；失败即失败，不重试吞异常 |

`--full` 使用 **Testcontainers 独立 MySQL**，不会对生产 compose 数据卷灌合成流水。生产库禁止用倍增 INSERT 造百万行。

## 2. 怎么跑

```bash
./deploy/perf.sh --check   # Flyway 是否声明热路径索引；不需要 Docker
./deploy/perf.sh --smoke   # 运行中的 compose MySQL：SHOW INDEX + 只读 EXPLAIN
./deploy/perf.sh --full    # JDK 21 + Docker：4096 行冒烟 + 百万行 + 50 并发（Testcontainers）
```

CI「部署资产」跑 `--check`（经 `install.sh --check`）和 `--smoke`（在 `monitor.sh` 之后）。后端 `mvn verify` 跑索引目录单测，不跑百万行。MySQL 8.4 integration-db 跑有界冒烟（8 并发 + 4096 行 EXPLAIN）。

百万行要几分钟，只在有 Docker 的开发机或演练机执行 `--full`。

## 3. 慢查询治理

生产 MySQL 容器打开：

- `slow_query_log=ON`
- `long_query_time=1`（秒）
- `log_output=FILE`（文件在数据卷 datadir，容器内主机名-slow.log）

查看：

```bash
docker compose --project-directory deploy -f deploy/docker-compose.yml --env-file deploy/.env \
  exec mysql sh -c 'ls -l /var/lib/mysql/*slow*.log; tail -n 50 /var/lib/mysql/*slow*.log'
```

不要开 `log_queries_not_using_indexes`（空表/小表会刷屏）。收发存汇总按「期末前全部流水」聚合，本来就要读历史，不是漏索引。

### 热路径索引（已有 + 本刀补的）

| 表 | 索引 | 用途 | 来源 |
|---|---|---|---|
| inventory_balance | uk_inventory_balance_dim (tenant_id, warehouse_id, product_id, batch_id) | 过账 `SELECT … FOR UPDATE` | V10 |
| inventory_transaction | uk_inventory_txn_idempotency (tenant_id, idempotency_key) | 幂等重放 | V10 |
| inventory_transaction | idx_inventory_txn_dim (tenant_id, warehouse_id, product_id, id) | 最近成本 / 台账按维倒序 | V10 |
| inventory_transaction | **idx_inventory_txn_src (tenant_id, src_doc_no, src_line_no)** | 勾稽/COGS/红冲按来源单号点查 | **V38** |
| voucher | uk_voucher_source / idx_voucher_period / idx_voucher_status | 自动凭证幂等、按账期汇总 | V19/V20 |
| voucher_line | idx_voucher_line_account / idx_voucher_line_head | 试算、报表 JOIN | V19 |

V38 的证据：一致性规则 6/12/13/16 等对 `inventory_transaction` 按 `src_doc_no + src_line_no` 做相关子查询。缺该索引时 EXPLAIN 为 `type=ALL`；加上后为 `ref` + `idx_inventory_txn_src`。过账写路径不改，仍只允许 `InventoryService` 插流水。迁移用 `ALGORITHM=INPLACE, LOCK=NONE`，已有流水的库升级时尽量不阻塞写入。

清单真源：`deploy/perf/required-indexes.txt`，`./deploy/perf.sh --check` 与 `RequiredLedgerIndexCatalogTest` 一起守门。

未加 `(tenant_id, created_at)`：收发存「期末=Σ(created_at < toExclusive)」在查到今天时几乎等于扫完全表历史，二级时间索引省不了这趟聚合。有仓库+商品过滤时走 `idx_inventory_txn_dim`。

## 4. 测到的上限怎么读

冒烟（CI / `--smoke`）证明：**计划用索引**，不是证明 50 人在某台 2C 机器上的绝对 TPS。

`--full` 打印：

```
[M8-T05] full seed rows=1048576 in …ms
[M8-T05] 库存入库 full-inv users=50 p50=… p95=… max=… errors=0
[M8-T05] 采购入库过账 full-pr users=50 p50=… p95=… max=… errors=0
```

断言：0 错误、对账恒等式、p95 &lt; 10s（CI/共享机宽松上限）。把实际 p50/p95 记进 [测试-M8-T05性能基线.md](./测试-M8-T05性能基线.md)。若某台小机器 p95 接近上限，先看慢查询日志和是否所有人打同一 SKU。

## 5. 和安装 / 监控的关系

- `./deploy/install.sh --check` 会跑 `perf.sh --check`
- CI 在 `monitor.sh` 之后跑 `perf.sh --smoke`（只读，不影响 restore-smoke）
- TLS 默认、`restore-smoke`、`monitor.sh` 行为不变
- **禁止改 `web-dist/`**；不引入 k6 SaaS / Grafana；Flyway 仅 V38 这一条证明过的二级索引
